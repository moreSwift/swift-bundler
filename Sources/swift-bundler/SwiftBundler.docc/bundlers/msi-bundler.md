# MSI bundler

A bundler that produces Windows MSI installers.

## Overview

The MSI bundler is the recommended bundler to use when distributing Windows
applications.

The output of the MSI bundler is not directly runnable, so it is incompatible
with the `swift-bundler run` command.

> Warning: On Windows, Swift Bundler must be run from the Native Tools Command
> Prompt, which can be located in the Windows start menu.

## Usage

### Create an MSI installer

```sh
swift-bundler bundle --bundler windowsMSI
```

### Create an optimized MSI installer

```sh
swift-bundler bundle --bundler windowsMSI -c release --strip
```

## WiX

The MSI bundler uses [WiX](https://www.firegiant.com/wixtoolset/) to create MSIs. WiX builds are configured using WXS files.

> Note: The WXS file generated by Swift Bundler can be found at `.build/bundler/apps/YourApp/project.wxs`.

## Customizing installers

The `msi.wxs_extras` app configuration field allows you to provide additional WXS configuration objects which get appended to the `project.wxs` file that the MSI bundler generates.

Common customizations performed using `msi.wxs_extras` are,

- [Automatically launching your app on successful installation](#Automatically-launching-your-app-post-install)
- [Running setup executables during installation](#Running-a-setup-executable-during-installation)

Refer to the [WXS reference docs](https://docs.firegiant.com/wix/schema/wxs/) for detailed information on available elements.

### WXS in TOML

The syntax that Swift Bundler's `msi.wxs_extras` configuration field uses is designed to mirror the WXS XML format in TOML while also being ergonomic to write,

- Elements translate to TOML tables (dictionaries),
- The element's XML tag name is stored in the `tag` field of the table,
- Raw text content (between the opening and closing tags) is stored in the `content` field of the table,
- Child elements (between the opening and closing tags) are stored in the `children` field of the table, and
- Attributes become standalone fields of the table

There are 3 special fields: `tag`, `content`, and `children`. Everything else gets interpreted as an attribute.

### WXS sample conversion

To illustrate, here is some some arbitrary XML along with an app containing this fictitious WXS element in its TOML configuration file. First, the XML,

```xml
<Heart BPM="100">
  <Ventricle Side="left" Health="90%"></Ventricle>
  <Ventricle Side="right" Health="85%"></Ventricle>
  <Stent Age="5y">Bob's first stent</Stent>
</Heart>
```

And here's the same WXS/XML element, but represented as a TOML configuration object,

```toml
[apps.YourApp]
msi.wxs_extras = [
  {
    tag = "Heart",
    BPM = "100",
    children = [
      { tag = "Ventricle", Side = "left", Health = "90%" },
      { tag = "Ventricle", Side = "right", Health = "85%" },
      { tag = "Stent", Age = "5y", content = "Bob's first stent" },
    ],
  },
]
```

### Using WiX extensions

WiX provides an [extension system](https://docs.firegiant.com/wix/tools/wixext/) that allows you to install extensions that extend the functionality of WiX. Swift Bundler allows you to configure WiX extensions that your app's build depends on,

```toml
[apps.YourApp]
msi.wix_extensions = [
  "WixToolset.Util.wixext/6.0.0",
]
```

It's currently not possible to use custom elements from WiX extensions; it's only possible to use properties and files provided by extensions (such as the custom actions DLL from `WixToolset.Util.wixext`). Comment on [issue #210](https://github.com/moreSwift/swift-bundler/issues/210) if you'd like such a feature.

### Default components

Swift Bundler's MSI bundler generates two `Component`s by default,

- `MainExecutable`: your app's main executable
- `Shortcut`: your app's start menu shortcuts

You can refer to these components in custom actions with the `[#ComponentName]` syntax that WiX provides. This is particularly useful when you need the path of your app's main executable.

### Automatically launching your app post-install

Our recommended approach is to use the [`WixShellExec`](https://docs.firegiant.com/wix/tools/wixext/util/#wixshellexec-custom-actions) custom action from `WixToolset.Util.wixext` to launch your application. You *can* use a standard `ExeCommand` custom action, but that may lead to your application opening in the background.

```toml
[apps.YourApp]
# ...
msi.wix_extensions = [
  "WixToolset.Util.wixext/6.0.0",
]
msi.wxs_extras = [
  {
    tag = "Property",
    Id = "WixShellExecTarget",
    Value = "[#MainExecutable]",
  },
  {
    tag = "CustomAction",
    Id = "LaunchApplication",
    BinaryRef = "Wix4UtilCA_$(sys.BUILDARCHSHORT)",
    DllEntry = "WixShellExec",
    Impersonate = "yes",
  },
  {
    tag = "InstallExecuteSequence",
    children = [
      {
        tag = "Custom",
        Action = "LaunchApplication",
        After = "InstallFinalize",
        Condition = "NOT Installed OR (Installed AND NOT REMOVE)",
      },
    ],
  },
]
```

Note the `Condition` that we provide to the `Custom` element in the `InstallExecuteSequence` array. Without that condition, your custom install action (named `LaunchApplication`) will also run when your installer gets invoked to repair/modify/uninstall your application.

### Running a setup executable during installation

To run executables as custom installation steps, we recommend using the [`QuietExec`](https://docs.firegiant.com/wix/tools/wixext/quietexec/) custom action from `WixToolset.Util.wixext`. `QuietExec` hides the command prompt window that would usually show when running an executable on Windows.

The following snippet demonstrates how to create a custom installation step (called `RunSetupExe`) that invokes an executable named `setup.exe` from the app's installation folder (`C:\Program Files\YourApp`),
```toml
[apps.YourApp]
# ...
msi.wix_extensions = [
  "WixToolset.Util.wixext/6.0.0"
]
msi.wxs_extras = [
  {
    tag = "SetProperty",
    Id = "RunSetupExe",
    Value = '"[InstallFolder]setup.exe"',
    Before = "InstallWindowsAppRuntime",
    Sequence = "execute",
  },
  {
    tag = "CustomAction",
    Id = "RunSetupExe",
    BinaryRef = "Wix4UtilCA_$(sys.BUILDARCHSHORT)",
    DllEntry = "WixQuietExec",
    Execute = "deferred",
    Return = "check",
    Impersonate = "no",
  },
  {
    tag = "InstallExecuteSequence",
    children = [
      {
        tag = "Custom",
        Action = "RunSetupExe",
        After = "InstallFiles",
        Condition = "NOT Installed OR (Installed AND NOT REMOVE)"
      },
    ],
  },
]
```

The `Value` attribute of the `SetProperty` element is the command that gets run by the `CustomAction` element with the matching id. The double quotes surrounding the exe's path are important because the value gets interpreted as a shell command, and the path will contain spaces (because the executable we've specified is a descendant of `Program Files`).

To add another installation step, duplicate the `SetProperty` and `CustomAction` actions replacing their matching ids with a new matching value. After that, duplicate the `Custom` element in the `InstallExecuteSequence` and update its `Action` attribute to match your newly chosen action id.

Optionally, you can update the `After` attribute to impose an ordering. Its value can be any action id, and `InstallFiles` happens to be the built-in action that WiX recommends you should run your custom setup executables after.

Note the `Condition` that we provide to the `Custom` element in the `InstallExecuteSequence` array. Without that condition, your custom install action (named `RunSetupExe`) will also run when your installer gets invoked to repair/modify/uninstall your application.

> Warning: If you forget to include a suitable `Condition`, your app may become impossible to uninstall, as the installer will attempt to run your setup executable after it has already removed all of the files (as silly as it may sound), which will fail and cause the uninstaller to revert.

## Uninstalling apps with broken uninstallers

Incorrect WXS customizations can occasionally make apps impossible to uninstall conventionally. An easy way for that to happen is for a custom action to omit a `Condition`, causing it to run during the uninstallation process and potentially causing the uninstaller to consistently fail.

The easiest way to resolve this is to install Microsoft's Install and Uninstall Troubleshooter. Microsoft doesn't advertise the troubleshooter for Windows 11, but the Windows 10 version works fine on Windows 11,

1. Download Microsoft's [Install and Uninstall Troubleshooter](https://aka.ms/Program_Install_and_Uninstall)
2. Open the application and click next 
3. When prompted what you're having issues with, select `Uninstalling`
4. Select the app that you're unable to uninstall
5. If it asks you what you want to do, and `try uninstall` is an option, then select that

In my experience, the troubleshooter will manage to uninstall the problematic app. If the app still appears in `Installed apps` (or `Apps & Features` on Windows 10), then attempt to uninstall it one more time.

## Debugging broken installers

MSI installer error messages are often very generic. To force an installer to produce a log, you can run it using `msiexec` with a few special arguments,

```sh
msiexec /i .\YourInstaller.msi /L*V .\output.log
```
